# DSH 长期记忆：当前架构与理论对照

> 更新：2026-11-06 · 对应版本 `@heixui/dsh-session-suite@0.4.0`
> 目的：把实际实现摆出来，逐条对照李博杰《AI Agents in Depth》第 3 章的框架，标出「已对齐 / 已实现但有限 / 明确不做」。
> **0.4.0 已落地的改动用 ✅ 标注；刻意不做的用 ⛔ 标注并写明理由。**

## 零、0.4.0 做了什么

| 项 | 改动前 | 改动后 |
|---|---|---|
| 重复记忆 | 1 个主题 7 条（1 fact + 2 summary + 3 rule） | 6 轮维护后稳定不增长；存量已合并归档 |
| 常驻层 | 2 条扁平记忆，与「本轮相关」混在一起 | 5 张主题卡片，两块分区标注 |
| 情景记忆 | **完全没有** | `kind: 'episode'` + occurredAt/context/outcome，衰减加倍 |
| dense 重排 | 架构有，默认关，权重未验证 | **默认开**，权重经实测校准为 1.0（MRR 0.535→0.760） |
| 隐私分级 | **完全没有** | public/internal/secret 三级，默认 internal，secret 永不注入/导出 |
| 隐式队列 | 70% 合法候选被误杀，且空队列无解释 | 移除误杀过滤器；空队列显示具体原因 |

## 一、一句话总览

当前实现是**双层记忆架构的简化版**：上层是每轮注入的常驻摘要（Resident），下层是按需召回的细节（Recall）；但**缺少「常驻概览」这一层的结构化组织**，也**没有真正的重排序模型默认启用**。

## 二、实际数据流（代码事实）

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. 写入                                                          │
│                                                                  │
│   用户说「记住：X」          → 显式写入（直通，不排队）           │
│   模型调用 memory 工具       → 显式写入（直通，不排队）           │
│   每轮结束 turn/end          → 隐式提取 → pending.json 队列      │
│                                  ↓ 用户点「保留」才入库            │
│   maintain()（30 分钟一次）  → 聚类成 summary / 按 tag 生成 rule   │
│                                 → 超阈值归档进 cold/              │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 2. 读取（每轮 prompt 注入）                                       │
│                                                                  │
│   agent/pre-step 钩子                                            │
│      ↓                                                           │
│   buildRecallText()                                              │
│      ├─ engine.select(query, limit=6)      ← 按相关性            │
│      │    ├─ 三路词法召回 + RRF 融合                              │
│      │    ├─ [可选] dense 余弦重排（默认关闭）                     │
│      │    ├─ 剔除 0 分候选、matched≠true 剔除                     │
│      │    └─ injectionTier(topScore) 决定注入几条                 │
│      │                                                           │
│      └─ 常驻层 residentLimit=2            ← 按重要度，与问题无关   │
│                                                                  │
│   合并成 markdown 块 → systemPrompt.context({ order: 900 })       │
└─────────────────────────────────────────────────────────────────┘
```

### 存储格式

| 位置 | 内容 |
|---|---|
| `memory/global.json` | 跨工作区记忆 |
| `memory/workspaces/<sha256前16位>.json` | 按工作区隔离 |
| `memory/cold/*.json` | 归档冷库（低分/超期） |
| `memory/pending.json` | 隐式候选队列（等用户确认） |
| `memory/maintenance.json` | 维护时间戳、指纹、上次报告 |
| `memory/workspaces.json` | 工作区 key → 可读路径（哈希单向，必须另记） |

### 评分公式（四因子）

```
score = 0.35×频率 + 0.30×时间衰减 + 0.15×情感权重 + 0.20×独特性
```

- 时间衰减：`decayDays = 60` 天半衰期
- 独特性：与库内其他条目相似度越低越高（防重复）
- 阈值：`compress ≥ 0.45`、`archive ≤ 0.25`

### 最终排序

```
rank = 融合名次分×0.75 + 重要度×0.20 + 工作区加成 0.05
      + [可选] dense余弦×0.15   ← 上限 0.15，不能压过词法精确匹配
```

## 三、逐条对照第 3 章框架

### 3.1 记忆层次

| 书中层次 | 我们的实现 | 状态 |
|---|---|---|
| 用户记忆（个性化） | `workspace` 作用域，按 cwd 哈希隔离 | ✅ 已对齐 |
| 知识库（集体共享） | `global` 作用域 | ✅ 已对齐 |
| — | 但没有「知识库」那种结构化组织（索引、RAPTOR、GraphRAG） | ❌ 未做 |

**关键差距**：书里的知识库是**面向所有用户共享的集体知识**，我们的 `global` 只是「所有工作区共享」，尺度完全不同。我们**没有跨用户共享能力**，也不应该有（隐私）。

### 3.2 三层次评估

书里指记忆价值的三层评估：**即时相关 / 长期有用 / 噪声**。

| 我们的机制 | 对应 |
|---|---|
| `matched === true` 过滤 | 即时相关（有词法证据） |
| 四因子评分 + 时间衰减 | 长期有用（频率高、常用、独特） |
| `injectionTier(topScore)` | 噪声抑制（分数低就少注入） |
| `TRANSIENT_HINTS` | 噪声抑制（识别「临时/这次/帮我」） |

**部分对齐**：有评估，但是**规则式**的，不是模型判断。书里描述的是**用 LLM 做三层次判断**。

### 3.3 四种存储格式

| 格式 | 我们的实现 |
|---|---|
| 纯文本 / Markdown | ✅ 记忆文本本身 |
| JSON 结构化 | ✅ `entries[]` 带 id/scope/score/tags/factKey |
| 向量 | ⚠️ **仅内存缓存**，不落盘（`denseCache`） |
| 图结构 | ❌ 未做（书里的 GraphRAG） |

### 3.4 认知类型：情景 / 语义 / 程序

| 类型 | 我们的字段 | 状态 |
|---|---|---|
| 语义（事实） | `kind: 'fact'` | ✅ |
| 程序（规则/做法） | `kind: 'rule'` | ✅ |
| **情景（什么时候发生了什么）** | **`kind: 'episode'`** | ✅ **0.4.0 新增** |

情景记忆带三个额外字段：`occurredAt`（发生时间）、`context`（当时在做什么）、`outcome`（结果/教训）。

**衰减加倍**：`EPISODE_DECAY_FACTOR = 0.5`，60 天半衰期对情景变成 30 天。理由是「周二部署挂了」很快失去行动价值，而「项目用 pnpm」能真很多年。衰减锚点是 `occurredAt` 而非写入时间——补录一件旧事不会让它变新。

**为什么这个缺口重要**：用户原话说「会话期间压缩对话记录可能就把图片想表达的内容覆盖了」——情景类信息恰恰不能靠对话流水承载，它需要一个带时间戳的独立类型。

### 3.5 记忆框架：Mem0 / Memobase

| 框架特点 | 我们的对应 |
|---|---|
| Mem0：抽取-更新-删除三阶段 | ⚠️ 相似但简化：抽取（隐含）+ 更新（factKey 覆盖）+ 删除（归档） |
| Memobase：基于用户画像的分层 | ❌ 未做（我们没有画像层） |

**我们没有实现「记忆更新」的完整语义**。目前的 `factKey` 只是「同 key 后写覆盖前写」，不是书里那种「新信息与旧记忆冲突时判断该信谁」。

### 3.6 压缩整理

| 书中做法 | 我们的实现 |
|---|---|
| 定期压缩相似记忆 | ✅ `clusterMinSize=2` 时合并成 summary |
| 按主题抽象出规则 | ✅ `ruleMinSize=3` 时按 tag 生成 rule |
| 归档低价值 | ✅ `archive ≤ 0.25` 进 cold |

**这块相对完整**，但实测有 bug：规则生成会把整组记忆拼成长文（已修，加了 `maxMemoryChars` 上限），而且**压缩阶段会互相喂**（阶段 3 生成 rule → 阶段 2 聚成 summary 归档 → 下轮阶段 3 又重建）。

### 3.7 隐私分级

**✅ 0.4.0 已做。** 三级：`public` / `internal` / `secret`。

- 默认 `internal`——**不是 public**。判断错的代价不对称：偏向隐私只损失一点便利，偏向公开会泄漏。
- `secret` 自动识别：密码、token、身份证、银行卡、手机号、邮箱、私钥、api key
- `internal` 识别：工资、存款、房租、病历、家庭住址等个人但非凭据的主题
- `secret` **永不注入 prompt**（凭据不是上下文，注入等于复制进每一次请求）
- `secret` **永不导出**，`internal` 也不导出（分享文件会离开这台机器）
- 导出时统计并报告 `excluded` 数量——静默丢数据看起来像数据丢失

**为什么这条必须做**：在此之前，一个写进 `workspace` 的密码会被注入每一轮 prompt，并被打包进每一次分享导出。scope 说的是「存在哪」，privacy 说的是「谁能看」，这是两个问题。

### 3.8 文档分块

**未做，也不需要**——记忆不是文档，单条上限 300 字符，不存在分块问题。

书里的分块是为「知识库」服务的（一份 PDF 怎么切），我们的场景是「一句话事实怎么存」。

### 3.9 多模态提取

**⛔ 明确不做。** 两条理由，第二条是决定性的：

1. 视觉模型调用有成本，而记忆本身是「一句话事实」，不值得为每条记忆付一次识图费用。
2. **用户原话**：「会话期间压缩用户和 agent 对话记录可能就把图片想表达的内容覆盖了」——多模态提取的信息写进记忆后，仍然会经历同样的压缩与衰减，提取了也留不住。真正的图片信息该留在会话里，不该进长期记忆库。

### 3.10 稠密 / 稀疏嵌入与混合检索

| 书中 | 我们 |
|---|---|
| 稠密（embedding） | ⚠️ 已实现架构，**默认关闭** |
| 稀疏（BM25） | ✅ 两路：bigram BM25 + 单字 IDF 覆盖率 |
| 第三路 | ✅ jieba 词表 BM25（书中未提，我们加了） |
| 混合方式 | ✅ RRF 按名次融合（不是分数相加，这点与书中一致） |

**这是目前最接近书中描述的部分。**

### 3.11 结构化索引：RAPTOR / GraphRAG

**⛔ 明确不做（当前阶段）。**

理由：书里的 RAPTOR 是「递归摘要成树」，GraphRAG 是「实体关系图」，二者都假设库里有**成百上千条**互相引用的内容，需要层级来导航。我们的库是 40-50 条个人事实，一层 tag 分组（0.4.0 的常驻卡片）已经足够；再加一层索引，成本（维护复杂度 + 注入预算）会超过收益。

**触发条件**：如果单工作区条目超过约 300 条，或出现「同一主题下还有明显子主题」的实际情况，再考虑。现在做是过早优化。

### 3.12 文件系统范式 / 智能体化 RAG

**未做。** 书里描述的是让 Agent 自己决定去读哪个文件、读几次；我们是**固定一次注入 6 条**，Agent 没有主动权。

### 3.13 上下文感知检索

| 书中 | 我们 |
|---|---|
| 根据当前上下文调整检索 | ⚠️ 部分：`injectionTier` 按分数调整数量 |
| 多轮对话中的追问理解 | ❌ 未做（每轮独立算 query） |

**明确缺口**：用户问「那它为什么慢？」，我们的 `query` 就是这句话本身，不含上文。书里的上下文感知检索会把前几轮一起考虑。

### 3.14 重排序（Rerank）

**✅ 0.4.0 已实测启用。**

架构：三路词法粗排 → RRF 融合 → **dense 余弦精排**（只对词法已命中的前 24 个候选）。

**实测数据**（`tools/probe-dense-rerank.mjs`，8 条改写查询 vs 真实库）：

| dense 权重 | recall@5 | MRR |
|---|---|---|
| 关闭 | 1.000 | 0.535 |
| 0.15（初版） | 1.000 | 0.546 |
| 0.5 | 1.000 | 0.708 |
| **1.0（采用）** | **1.000** | **0.760** |
| 2.0 | 1.000 | 0.723 |
| 8.0 | 1.000 | 0.629 |

**关键结论**：
- recall@5 从未下降——dense 只改排序不改候选集
- MRR 提升 42%，曲线有明显极大值，不是「越大越好」
- 初版 0.15 几乎无效，是**查询集太简单**（词法已全部排对）造成的误判，不是 dense 无用

**同义查询实证**（模型 `bge-base-zh-v1.5`，768 维）：

| 对比 | cosine |
|---|---|
| `checkpoint 怎么回滚` ↔ `快照必须在每轮结束拍` | **0.515** |
| `记忆为什么排错序` ↔ `检索要用查询覆盖率` | 0.429 |
| `checkpoint 怎么回滚` ↔ `今天天气怎么样` | **0.196** |

同义比无关高 **2.6 倍**——这正是纯词法做不到的（实测零匹配）。

**默认值取舍**：embedding 默认**关闭**。用户不装模型时功能完全正常，只是少了同义召回。模型与运行时都不进 npm 包。

## 四、书中的「双层记忆架构」vs 我们的实现

书里的结论：**Advanced JSON Cards 常驻概览 + 上下文感知检索按需取细节**。

| 书 | 我们 | 差距 |
|---|---|---|
| JSON Cards 常驻概览 | `residentLimit=2` 条常驻记忆 | **数量太少，且无结构** |
| 按需取细节 | `recallLimit=6` 条按相关性 | ✅ 有 |
| 上下文感知 | — | ❌ 无 |

**我们的「常驻层」是退化版**：书中是结构化的卡片集合（按主题组织、可遍历），我们是「重要度最高的 2 条」。用户看到的 6 条里有 2 条永远相同，就是这个原因。

## 五、真实存在的问题（0.4.0 后的状态）

### 5.1 重复记忆泛滥 — ✅ 已修

同一主题在库里有多份（0.3.x 实测）：

```
mem_070065e00ae2  kind=fact      缓存命中率归因…
sum_504aeaaa266a  kind=summary   规则（dsh）：缓存命中率归因…
sum_7512b7147353  kind=summary   规则（dsh）：缓存命中率归因…
rule_4ba6b3bfb845 kind=rule      规则（dsh）：缓存命中率归因…（已归档）
rule_c11c2716d36c kind=rule      （同上）
rule_db9856466d13 kind=rule      （同上）
```

**根因**：summary 的去重只查活动库、且比较原始拼接文本。成员顺序变化或成员已归档就认不出「这条已经存在」，于是反复生成。规则生成早就修过这个洞，聚类阶段没有。

**修法**：去重键改为**排序后的内容摘要**（`summaryDigest`），并**同时搜索冷库**。

**验证**：连续 6 轮 `maintain()`，计数从「每轮 +2」变成第 2 轮后完全稳定（`selftest-memory-dedupe.mjs` 打印的表）。

**存量清理**：`tools/dedupe-memories.mjs` 按内容指纹合并，保留最完整的一条，其余归档到冷库并标 `mergedInto`。已清理 2 条，全部有备份。

### 5.2 冷归档没真正清理 — ⚠️ 设计如此

归档条目仍在库中（`archived: true`, `score: 0`），只是不参与 recall。这是有意保留的：`list()` 需要能看到历史，用户也要能恢复。**但常驻卡片和注入路径都必须排除它们**——0.4.0 已确认排除，并有测试守住。

### 5.3 常驻层与召回层语义混淆 — ✅ 已修

用户看到「输入问题会召回什么」下面列了 6 条，以为全是相关性排序。实际是 4 条相关 + 2 条常驻。

**修法**：常驻层改为主题卡片，注入文本分两段并明确标注：

```
### 与本次提问相关
- [本工作区] …

### 库内概览（与本次提问无关，供你了解已积累的内容）
- 错误教训（7 条）：…
- 偏好（2 条）：…
```

**实测效果**：从「1 张卡 621 字符」变成「4 张卡 290 字符」，用户能看到库里有哪几类内容。

### 5.4 单条长记忆撑爆卡片预算 — ✅ 已修

一条 280 字符的记忆做了卡片摘要，整张卡 621 字符，超过 600 预算，把其他主题全挤掉。

**修法**：卡片摘要截断到 60 字符（`residentCardSummaryChars`）。截断在这里可以接受——卡片是指针不是记忆本体，全文仍可被 recall 取到。

### 5.5 隐式队列 70% 误杀 — ✅ 已修

模型已经按提示词判断过重要性，代码却对**模型输出**再做一次关键词过滤，要求必须含「以后/一律/总是/偏好」。模型输出是改写过的陈述句，实测 10 条合法候选被杀 7 条。

**修法**：队列路径移除 `DURABLE_HINTS`，只保留「格式不合法」的检查。该正则仍用于**显式写入**的 affect 打分（那里处理的是用户原话，用法正确）。

### 5.6 空队列无法解释 — ✅ 已修

`pending.json` 曾完全不存在，且设置页什么都不显示。现在每个 early return 都记录原因，设置页显示：

> 当前没有待确认条目。上次检查结果：*（具体原因）*

| P5 | 上下文感知检索（带上文） | 上下文感知检索 | ⏸ 未做，见下 |

| ⛔ | 智能体化 RAG | 文件系统范式 | 明确不做（固定注入 6 条已够用，让 Agent 自己遍历文件是另一种产品） |

| ⛔ | 跨用户知识库 | 知识库 | 明确不做（个人助手，不共享给他人） |

### P5 上下文感知检索为什么暂缓

现在每轮的 `query` 就是当前这句话，不含上文。用户问「那它为什么慢？」，检索不知道「它」指什么。

**这是真实缺陷**，但修它需要判断「哪些上文值得拼进 query」——拼少了没用，拼多了反而稀释。没有可靠的判据时，贸然实现会退步。暂缓，等有具体的失败案例再动手。

---

## 七、对齐度评估（0.4.0 实测）

| 维度 | 0.3.x | 0.4.0 | 依据 |
|---|---|---|---|
| 混合检索 | 80% | **90%** | 三路词法 + RRF + dense 精排（权重实测校准），缺跨语言同义 |
| 压缩整理 | 70% | **85%** | 聚类/规则/归档齐备且幂等（6 轮验证） |
| 双层架构 | 40% | **65%** | 常驻卡片有结构、分主题、有预算；仍无层级索引 |
| 认知类型 | 60% | **90%** | fact/rule/summary/episode 四类齐全 |
| 重排序 | 50% | **85%** | 默认启用，权重有实测依据（MRR +42%） |
| 隐私分级 | 0% | **75%** | 三级 + 自动识别 + 导出/注入双过滤；UI 编辑待完善 |
| 结构化索引 | 0% | **0%** | 明确定不做 |
| 上下文感知 | 10% | **10%** | 明确定暂缓 |

**一句话**：0.3.x 的瓶颈在「组织」，0.4.0 把组织补齐了（重复清理、常驻卡片、情景类型），并让检索从「能找到」升级到「按相关性排对」。仍未做的三项都写了理由，不是遗漏。

**最诚实的一句**：检索层现在接近书中描述，但**上下文感知检索是明显的功能缺口**——用户问「它为什么慢」时，系统确实不知道「它」是什么。这是下一步真正值得做的，不是索引图。
